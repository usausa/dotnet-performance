# 🧹 ライブラリの無駄の見直し

[README](../README.ja.md) のパターンカタログは「どう書けば速いか」を扱う。本書は「**稼働しているコードのどこを見れば無駄が見つかるか**」の観点集で、見直しの入口として使う。

**参考実測の出典:** 本書の数値は、実運用している 7 つのライブラリ(UI 4 種・変換・MVVM・コア)を 2026-11 に見直したときの実測。**Zen 3 機・.NET 10 の JIT** で測ったもので、カタログの基準環境(HX 370 / x86-64-v4)の値ではない。採用判断は各パターンの実測結果を見る。

---

## 🧭 パターン ID を持たない観点

### W-01 全体を作り直している

- **見つけ方:** コレクションの変更通知を受け取るコードで、`NotifyCollectionChangedEventArgs` の `NewItems` / `OldItems` を使わずに、元の集合を全部走査して内部状態を作り直していないか
- **直し方:** 変更の種類ごとに差分だけ足し引きし、`Reset` と引数のない通知だけ全体を作り直す。購読の数え上げなら `Dictionary<T, int>` で個数を持つ
- **参考実測:** 5,000 件を一括追加する場面で **837 ms・697 MB → 8.1 ms・2.2 MB**。1,000 件の `Move` / `Replace` を 1,000 回でも 1.5〜1.7 倍速くなった
- **💥 の確認点:** 通知の引数に頼るので、引数を正しく出さない自作コレクションでは状態がずれる(標準のコレクションは正しく出す)。`Reset` で作り直す経路を必ず残す

### W-02 変わらないのに作る・通知する

- **見つけ方:** 「作り直した結果が前と同じ」場合の早期脱出があるか。同じクラスの他の操作(`Clear` 系・空の追加)が通知しないのに、1 つだけ通知していないか
- **直し方:** 先に件数と要素を比べて同じなら抜ける。差分を作るときは辞書の容量を指定し、`CollectionsMarshal.GetValueRefOrAddDefault` / `GetValueRefOrNullRef`(COL-07)で 1 回の探索にする
- **参考実測:** 1,000 件で変化のない `Refresh` を 1,000 回で **57.9 ms・123.5 MB → 8.3 ms・7.8 MB**。並びが変わる変更でも割り当てが約半分
- **💥 の確認点:** 通知が減るのは動作の変更。UI のバインドが「毎回評価し直される」ことに依存していないかを確かめる

### W-03 聞き手がいないのに引数を作る

- **見つけ方:** イベント・リクエストを発火する側で、`Handler is not null` を見る前に引数オブジェクトを作っていないか。同じ名前空間の仲間が先に確認しているなら、揃っていない方が無駄
- **直し方:** ハンドラを 1 回読み、null なら既定値を返して引数を作らない
- **参考実測:** 聞き手なしの 1 回が **3.9〜5.0 ns・24 B → 0.6〜0.8 ns・0 B**
- **💥 の確認点:** 戻り値の型が値型のとき、引数を作らない経路の既定値を決める(`null` を値型に戻すと `NullReferenceException` になるので `default` にそろえる)

### W-04 同じものを作り直して返す

- **見つけ方:** 名前の変換・正規化・エスケープで、**入力がすでに目的の形**でも新しいインスタンスを作っていないか。BCL の対応物(`JsonNamingPolicy.CamelCase` など)がそのまま返すかを確認する
- **直し方:** 変換が必要かを先に判定し、不要なら受け取ったインスタンスをそのまま返す
- **参考実測:** すでに小文字のキーで **11.9〜13.9 ns・32〜48 B → 1.9〜5.7 ns・0 B**。2 万件のランダムな入力では 14,038 件がそのまま返る側に乗った
- **💥 の確認点:** 同じインスタンスが返るようになるため、`ReferenceEquals` で区別していた呼び出し側には差が出る(不変な型なら実害はない)

### W-15 動いていない間も動く

- **見つけ方:** ビヘイビア・添付プロパティ・購読を、**付いた時点**で開始していないか。UI フレームワークは画面を閉じても付属物を外さないことがあるため、「外されたとき」だけを終了条件にしていると動き続ける
- **直し方:** 可視性のライフサイクル(`Loaded` / `Unloaded` など)で開始・停止し、外されたときも停止する。同じライブラリの他の部品が既にその形なら揃える
- **参考実測:** 時間ではなく動作の誤り。閉じた後もタイマーがアクションを実行し続け、ビヘイビア・アクション・ViewModel が解放されない
- **💥 の確認点:** 画面が見える前は動かなくなり、戻ると間隔を数え直す。裏に回っても `Loaded` のままになるプラットフォームがあることも確認する

### W-16 使う側ごとに表を持つ

- **見つけ方:** 同じ変換表・キャッシュ・リフレクションが、複数のライブラリや複数の利用側に同じ形で存在していないか。差が「戻り値の既定値」程度なら共通化できる
- **直し方:** 1 つ下の層(共通のコアライブラリ)に置き、各ライブラリはそれを呼ぶだけにする。表と一緒に、リフレクションと抑止も 1 か所に集まる
- **参考実測:** 4 つの UI ライブラリが同じ列挙型→説明の表を持っていた。共通化とキーの見直しでヒット 1 回が **20.9〜27.5 ns → 14.3〜15.0 ns**、表を持たない場合は **181〜1,104 ns・120〜280 B**
- **💥 の確認点:** 公開 API が 1 つ増える。拡張メソッドにすると利用側の自作拡張と名前が衝突して `CS0121` でビルドが落ちうるので、静的メソッドにする

## 📏 見直しの進め方

1. **重い順に 1 件ずつ。** 案(現状・候補・影響・💥)を表にして出し、採否を決めてから作る。1 件ずつ入れて、前後を比べる
2. **写しで前と後を比べる。** リポジトリの写しに案を作り、同じ操作列(乱数の操作を数千〜数万手)で**結果・通知・例外を 1 行ずつ突き合わせる**。速さではなく「同じこと」を先に固定する
3. **並べて流せる確かめは並べて先に。** ビルド・テスト・AOT 発行・突き合わせは同時に流せる。**時間の計測だけは 1 つずつ**(並列は乱れる。割り当ては乱れない)
4. **わざと壊して、足したテストが落ちることを確かめる。** 直した箇所を元に戻す・条件を 1 つ外す、などの壊し方ごとに、落ちるテストの件数を記録する
5. **数値は直した成果物で測り直す。** 案の試作で測った値ではなく、ビルドした成果物(ハッシュを確認したもの)で再測する
6. **静的解析はまとめて 1 回。** 1 件ごとに流さず、変更がまとまった時点で流す
7. **警告を消すためだけの直しはしない。** 動作・速さ・割り当てを落とさないことを確認してから直す

## 🚫 見直して「無駄ではない」と判断したもの

同じ見直しで調べたうえで、直さないと決めた形。**同種のコードを見つけても手を入れない。**

| 形 | 理由 |
|---|---|
| 1 回だけ作る静的な表(型ごとのメタデータ・定数表) | 初期化時の 1 回で、ヒット経路には出ない(TYP-04 / TYP-06 の正しい形) |
| 作成時にしか通らないリフレクション | 全体のコストに対して無視できる割合(測った例では作成処理の約 0.15%) |
| 型で比較しているキャッシュのキー | 値の比較より速く、衝突もない |
| ライフサイクルのイベントで購読するトリガー | W-15 の正しい形 |
| 使い手のいない型への公開 API の追加(構造体の列挙子など) | 得は具体的な型で直接 `foreach` したときだけで、公開 API と動作が変わる |
| 辞書の 2 回の探索が数 ns の経路 | 1 回化で得られるのは数 ns だけで、アナライザの誤検出に対する抑止が複数必要になる |
| 標準ライブラリが同じコストを払っている形 | 標準と違う挙動を作る方が利用側の驚きになる(`List<T>.Find` が書き換えを見張らないなど) |
| 聞き手がいない間の遅延評価(W-01 の延長) | 画面にバインドする使い方では購読が常にあるので効き目がなく、絞り込み・並べ替えが呼ばれる時機と例外の出所が変わる |
